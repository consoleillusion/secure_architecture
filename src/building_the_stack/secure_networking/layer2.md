## Layer 2 - The Data Link Layer

### What Layer 2 is for

Layer 1 produces a stream of bits on a medium. That is not yet enough to communicate. A bitstream has no boundaries, no way to know where one message ends and the next begins. It has no addressing, every receiver attached to the same medium hears the same bits. And it has no integrity check, a bit corrupted by interference is indistinguishable from a bit deliberately transmitted. Layer 2 is the layer that solves these three problems together. It groups bits into **frames**, gives every network interface a hardware address so that frames can be directed to a specific recipient, and appends a check sequence at the end of each frame so that the receiver can tell whether what arrived is what was sent.

This is the first appearance of **structured data** in the dependency chain. At Layer 1 the data is undifferentiated, voltage transitions, light pulses, modulated radio waves, all carrying ones and zeros in a flat stream. At Layer 2 the data has shape: a header with a source and destination address, a payload, and a trailer with the frame check sequence. The frame is the first PDU in the stack that can be inspected, addressed, filtered, and reasoned about as a discrete object. Everything above Layer 2, packets, segments, application messages, depends on the frame existing first, because every higher PDU is constructed by encapsulation inside one.

It is also the first layer at which an explicit **trust decision** appears in the architecture. A bitstream cannot be trusted or distrusted; it is just energy. A frame, by contrast, claims to come from a particular hardware address and to be destined for another. That claim is unauthenticated by default. The layer's most important architectural property, and the source of nearly every security problem at this layer, is that it was designed in an era when the broadcast domain was assumed to be a cooperative environment. Every device on the same LAN was assumed to be honest. Every claim made in a frame header was assumed to be true. The protocols at Layer 2 are still the same protocols, and they still make the same assumption.

### What the layer actually creates

#### The frame

Every Layer 2 technology, Ethernet, Wi-Fi, PPP, defines a frame format. The details vary, but the structure is consistent: a header containing addressing information, a payload carrying the upper-layer PDU, and a trailer containing a frame check sequence (typically a CRC) that allows the receiver to detect bit errors introduced by the medium. The frame is the **PDU Transformation** that Layer 2 contributes to the dependency chain. Ethernet and Wi-Fi are the canonical examples. They take a Layer 3 packet and wrap it in a frame so that it can be carried across the local medium. Without that transformation there is no packet; without a packet there is no anything else.

Frame size is bounded. Standard Ethernet caps the payload at 1500 bytes, a number chosen in the early 1980s as a compromise between latency and efficiency. Jumbo frames extend this to 9000 bytes for environments where both endpoints and every intermediate device agree on a larger MTU. The architectural significance is small in either case, the MTU is a knob to tune, not a security property. What matters is that the frame is finite and self-describing, with a known beginning and a known end.

#### The MAC address

Every Layer 2 interface has a hardware address, a 48-bit identifier called a MAC address, typically assigned by the manufacturer. The address has no inherent geographical or topological meaning. It identifies an interface, not a location. Two interfaces on the same broadcast domain with the same MAC address will collide and produce undefined behaviour; two interfaces with different MAC addresses on opposite sides of a router are not Layer 2 neighbours at all and will never see each other's frames.

The MAC address is the addressing primitive that frames use. It is also the thing the architect has to remember is **not** an authentication primitive. A MAC address can be changed in software on virtually every operating system shipped in the last twenty years, with a single command. Any frame can be transmitted with any source MAC the sender chooses to put in it. The address is a label, not a credential. Treating it as a credential, whitelisting MAC addresses as if they identified a trusted device, is a category error that recurs throughout poorly designed Layer 2 deployments.

#### The broadcast domain

A broadcast domain is the set of interfaces that share a Layer 2 segment, all the interfaces that will receive a frame transmitted to the broadcast address `ff:ff:ff:ff:ff:ff`. Within a broadcast domain, every device is the Layer 2 neighbour of every other device. Routers terminate broadcast domains; switches extend them. This is the unit of Layer 2 scope, and it is also the unit of Layer 2 blast radius. Every attack the layer is vulnerable to is bounded by the broadcast domain in which it occurs. Architectures that treat the broadcast domain as a security boundary are wrong in a specific way: a broadcast domain is a **failure** boundary, not a **trust** boundary. Compromise at one host on a broadcast domain creates direct exposure to every other host on it, because the protocols at Layer 2 do not authenticate.

### Switches and what they actually do

A switch is the device that extends a broadcast domain across more than two interfaces. It does this by learning, dynamically, which MAC addresses are reachable through which of its physical ports, and forwarding each received frame only to the port where the destination MAC has been seen. The MAC address table, sometimes called the CAM table, is the data structure that records this information. When a frame arrives for a MAC address the switch has not yet learned, the switch falls back to broadcasting the frame out of every port other than the one it arrived on, in the hope that the destination will respond and the table can be populated.

A switch is therefore not a security device. It is an efficiency device. It exists to keep frames from being broadcast unnecessarily. The MAC table is a cache of routing information for frame forwarding, not an access control list. Two architectural facts follow from this directly.

First, the table is finite. A typical switch holds tens of thousands of entries. An attacker on the broadcast domain can fill the table by transmitting a flood of frames with random source MAC addresses, the **MAC flooding** attack, also called CAM overflow. Once the table is full, the switch can no longer learn new entries, and depending on its implementation it begins to fail open: every frame it receives for an unknown destination is broadcast out every port. The switch becomes, functionally, a hub. The attacker on the broadcast domain now sees every frame addressed to anyone on it. This is not a bug in any particular switch; it is a consequence of the layer's design. The MAC table has to be finite, because memory is finite, and it has to fail somehow when it overflows. Failing open is the choice that preserves connectivity, and most switches make it.

Second, MAC learning is automatic and unauthenticated. Any frame the switch receives from any port teaches the switch that the source MAC of that frame is reachable through that port. An attacker can move another host's MAC to their own port simply by sending a frame claiming to be that MAC. The switch will believe it. From that moment on, frames destined for the legitimate host will be delivered to the attacker. This is **MAC spoofing** at the table-poisoning level, and it requires no exotic capability, only the ability to send a frame.

The conventional response to both attacks is **port security**, configuring the switch to limit how many MAC addresses it will learn on each port, and to drop or shut down ports that exceed the limit. This works as a patch. It is also a clear example of a Layer 2 control bolted on to compensate for a property the layer should never have been assumed to provide. The port security configuration has to be applied to every port on every switch in the environment, kept in sync with the legitimate inventory of devices, and updated whenever something changes. It is procedural where it could have been architectural, and it depends on the switch vendor's implementation being correct, the configuration being correct, and the inventory being current. Each of those is an opportunity for the control to fail silently.

### ARP, the canonical PDU Address Translation problem

Layer 3 packets carry IP addresses. Layer 2 frames carry MAC addresses. To deliver a packet to a host on the same broadcast domain, the sending host needs to know the MAC address that corresponds to the destination IP. The Address Resolution Protocol, **ARP**, is the protocol that performs this translation.

ARP is the canonical example of a PDU Address Translation protocol. It does not transform a PDU into another PDU type. It translates an address from one layer's scheme into another so that the next Transformation can complete. Without ARP, Ethernet cannot fill in the destination MAC field of a frame, so no frame can be built, so no packet can be delivered. The dependency is hard. Remove ARP and the entire Layer 2 → Layer 3 boundary collapses for IPv4 traffic.

ARP is also entirely unauthenticated. An ARP request asks "who has IP address X?" and any device on the broadcast domain can reply "I do, my MAC is Y." The asker has no way to verify the reply. There is no signature, no challenge, no record of who is **supposed** to own which IP. The asker caches the reply and uses it to address subsequent frames. An attacker who replies faster than the legitimate owner, or who sends unsolicited replies, which most ARP implementations also accept, can substitute their own MAC for any IP on the segment. This is **ARP spoofing**, also called ARP poisoning, and it is the textbook attack against Layer 2.

The consequence is that the attacker becomes the next-hop MAC for the targeted IP. Frames addressed to that IP arrive at the attacker's interface. The attacker can drop them (denial of service), forward them to the real destination after inspection (a transparent man-in-the-middle), or replace their contents and forward modified versions onward. Nothing at Layer 2 detects this. Nothing at Layer 3 detects it either, because the packets arrive at their destination IP, they just take a longer path to get there. The attack lives entirely in the address resolution prerequisite that Layer 2 Transformation depends on.

The conventional response is **Dynamic ARP Inspection** (DAI), which has the switch validate ARP replies against a binding table of known IP-to-MAC mappings, typically learned from DHCP through a parallel feature called **DHCP snooping**. The chain of patches becomes visible quickly: DAI depends on DHCP snooping being enabled and correctly configured; DHCP snooping depends on knowing which switch ports are connected to legitimate DHCP servers (the "trusted" ports); the trust labels on the ports depend on the configuration being current; the binding table depends on every legitimate host using DHCP rather than configuring its address statically. Each link in this chain is a place where the control can fail without anyone noticing. It works in well-administered environments. It is not what the architecture should rely on.

### Spanning Tree, the assumption of a cooperative topology

Switches forward frames out every port except the one a frame arrived on. A network with redundant paths between switches will, by default, forward broadcast frames in a loop, the frame goes from switch A to switch B over one link, from B back to A over the redundant link, and around again forever, multiplying every time another switch learns the frame and rebroadcasts it. Within seconds the loop saturates every link in the topology. This is the broadcast storm. It does not require an attacker; a cabling mistake produces it.

The Spanning Tree Protocol, **STP**, was invented to solve this problem. The protocol elects one switch as the **root bridge**, computes the shortest path from every other switch to the root, and disables, by putting into a **blocking** state, any port that would create a redundant path. The result is a logical tree topology overlaid on a physical mesh: every switch has exactly one path to the root, no loops are possible, and if a link fails the protocol recomputes the tree to use the previously blocked redundant path. The port states, blocking, listening, learning, forwarding, describe the transitions a port goes through as the tree converges. Rapid Spanning Tree (RSTP) and Multiple Spanning Tree (MSTP) are evolutionary refinements that converge faster and allow per-VLAN tree calculation, but the underlying election mechanism is the same.

The election mechanism is the architectural problem. STP elects the root by listening for **BPDUs**, bridge protocol data units, and choosing whichever advertised bridge claims the lowest bridge ID. There is no authentication on the BPDU. Any device on the broadcast domain that emits a BPDU with a sufficiently low bridge ID becomes the root, and the entire spanning tree reconverges around it. An attacker who plugs into any switch port and emits a low-bridge-ID BPDU can become the root of the entire L2 topology. Frames begin flowing through the attacker's switch, or the attacker's laptop pretending to be a switch, because the protocol has obediently rebuilt the tree to make that the shortest path. This is **STP root hijacking**, and like ARP spoofing it requires only the ability to send the relevant frame.

The conventional patches are **BPDU guard** and **root guard**. BPDU guard disables a port if any BPDU is received on it, on the assumption that switch-to-switch ports are known and labelled and any other port should never see a BPDU. Root guard prevents a port from accepting a BPDU that would cause the root to change. Both depend on per-port configuration, applied correctly, kept current. Both are bolted on top of a protocol whose default trust model is that anyone on the broadcast domain is a legitimate participant in the topology.

### VLANs, segmentation enforced by configuration

A VLAN, Virtual LAN, defined by **IEEE 802.1Q**, is a way to partition a single physical switching infrastructure into multiple logical broadcast domains. Each VLAN is identified by a 12-bit tag carried in a header inserted into the Ethernet frame. A switch port is configured either as an **access port** belonging to one VLAN, in which case frames entering the port are tagged with that VLAN ID and frames leaving the port are stripped of their tag, or as a **trunk port** carrying tagged frames for multiple VLANs to another switch. The 12-bit field allows for 4094 usable VLANs, which is the limit usually quoted as the constraint that drove the development of VXLAN and other overlay encapsulations.

VLANs are useful, and they are used everywhere. They are also a textbook case of segmentation enforced by configuration rather than by structure. The separation between two VLANs exists because every switch in the path correctly applies the tagging rules: tagging on ingress, looking up the egress port for that VLAN, stripping the tag on egress to an access port, preserving it on egress to a trunk. A switch that misapplies these rules, through a bug, a misconfiguration, or a compromise, does not segment. The frames cross the VLAN boundary, and there is no mechanism above the switch that notices.

The most common misconfiguration is the **native VLAN**. A trunk port carries tagged frames for many VLANs, but it also has a native VLAN, a single VLAN whose frames are sent untagged across the trunk for backward compatibility with devices that do not understand 802.1Q. The trouble is that an access port set to the same VLAN as the trunk's native VLAN has no tag boundary at all. A device on that access port can send a frame with an explicit VLAN tag inside it; the switch sees an untagged frame on the access port (interpreting the embedded tag as part of the payload), forwards it onto the trunk untagged (because that is what the native VLAN does), and the receiving switch sees a tagged frame with the embedded VLAN ID and forwards it accordingly. This is **double-tagging VLAN hopping**. The defence is to never use a VLAN as both an access VLAN and a trunk's native VLAN, and ideally never to use the native VLAN feature at all, set the trunk to tag everything, including frames previously considered native. This works. It is, again, a configuration discipline that has to be applied consistently and verified continuously, with no structural mechanism that prevents the mistake.

The other vulnerability is **switch spoofing**. The protocols that negotiate trunks between switches, Cisco's Dynamic Trunking Protocol is the canonical example, can be spoofed by an attacker who claims to be a switch. A negotiated trunk gives the attacker access to every VLAN the trunk carries. The defence is to never auto-negotiate trunks. Configure trunk ports explicitly, and configure access ports to refuse trunk negotiation. Once again: a vendor-specific protocol, defaulted on, providing convenience by trusting the LAN, mitigated by configuration.

The architectural takeaway is that VLANs are a useful tool for **organisational** separation, keeping the printers off the same broadcast domain as the workstations, keeping the IoT devices in their own quarantine zone, but they are not a strong security boundary on their own. They are policy enforced by the faithful execution of configuration on every switch in the path. The strength of the boundary is the strength of the weakest configuration in the topology.

### VXLAN, moving the boundary, not solving it

**VXLAN**, Virtual Extensible LAN, encapsulates Ethernet frames inside UDP packets so that a Layer 2 broadcast domain can be carried across a Layer 3 network. The encapsulation is performed by **VTEPs**, VXLAN Tunnel Endpoints, which sit at the boundary between the Layer 2 domain and the Layer 3 underlay. The 12-bit VLAN ID is replaced by a 24-bit VXLAN Network Identifier, lifting the 4094-network limit to roughly 16 million.

VXLAN is widely used in data centres, where it is the substrate beneath much of what is sold as software-defined networking. It does not, however, change the analysis of Layer 2 from a security perspective. The same broadcast domain semantics, the same ARP, the same MAC learning, the same trust model, all of it now stretches across whatever Layer 3 reachability the underlay provides. The attack surface within a broadcast domain is unchanged; the attack surface has merely been extended geographically. An ARP spoofing attack inside a VXLAN segment behaves exactly as it would inside a physical VLAN, except that the attacker and the victim might be in different data centres. VXLAN moves the trust boundary; it does not strengthen it.

### Wireless, Layer 2 over a medium anyone can listen to

Wi-Fi is Layer 2 over a medium with a critical property: every transmission is heard by every receiver in range. The medium is fundamentally broadcast and fundamentally observable. Where Ethernet's broadcast domain is bounded by the physical reach of cables and the configuration of switches, Wi-Fi's broadcast domain is bounded only by the reach of the radio signal. A wireless network spilling into the parking lot or the floor below puts every frame transmitted on it within the eavesdropping range of anyone with an antenna.

The Layer 2 mechanisms, frames, MAC addressing, association, work much the same way as on Ethernet. The differences live in two places. First, every frame is, by default, captureable by every receiver in range; the only thing preventing that capture from being useful is encryption applied at the link layer. Second, association, the act of joining a network, is something the medium itself cannot prevent. A device chooses to associate with a network it can hear, and the network chooses to accept or reject the association. The mechanisms that make this safe are cryptographic and require a key that the unauthorised device cannot obtain.

**WPA2** introduced AES-CCMP encryption at the link layer and is still in widespread use. **WPA3** improves on it in several specific ways: it replaces the WPA2 four-way handshake with a Simultaneous Authentication of Equals (SAE) handshake that resists offline dictionary attack on the pre-shared key, it makes forward secrecy a requirement so that compromise of the PSK does not retroactively expose previously captured traffic, and it deprecates several legacy mechanisms that had become attack vectors. WPA3 is the right default for any new deployment.

Both WPA2 and WPA3 come in two modes. **Personal** mode uses a pre-shared key, every device knows the same passphrase, every device can decrypt every other device's traffic if it captures the handshake, and rotating the key requires reconfiguring every client. This is appropriate for home networks. It is not appropriate for an organisation. **Enterprise** mode uses **802.1X** for authentication, with each device authenticating individually against an authentication server, and unique session keys derived per association. WPA2-Enterprise and WPA3-Enterprise are the only acceptable modes for organisational Wi-Fi. The pre-shared-key model collapses the moment the key leaks or a single device is compromised, and at organisational scale that is a question of when, not whether.

The authentication itself happens through the **Extensible Authentication Protocol** (EAP) family. EAP is not a single protocol but a framework for many; the choice of EAP method is the load-bearing security decision. **EAP-TLS** is the one to choose. It performs mutual TLS authentication between the client and the authentication server, using certificates on both sides. Neither side trusts the other on the basis of a name or a password; both present certificates, both verify the other's certificate against a trusted CA, and only then is the session established. **PEAP** and **EAP-TTLS** wrap an inner password-based authentication inside a TLS tunnel; they are widely deployed and they are a step down from EAP-TLS. They retain the password as the credential, which means they retain every problem passwords have, mitigated only by the tunnel that protects the password in transit. For an architecture that takes the principles in the introduction seriously, EAP-TLS is the only acceptable choice. It places a certificate on every device, signed by the organisation's own CA, and it makes the absence of a valid certificate the same thing as the absence of network access. This is fail-safe defaults expressed at the Layer 2 attachment point.

**Rogue access points** and **evil twin attacks** exploit the fact that clients may associate with any access point advertising a familiar SSID. A rogue AP is one set up by an unauthorised party, sometimes inside the organisation by an employee who wants better Wi-Fi coverage, sometimes outside by an attacker. An evil twin specifically clones the SSID of a legitimate network in the hope that clients will associate with it instead. Both attacks fall apart if the client requires mutual authentication with a known authentication server. EAP-TLS, configured correctly with server certificate validation enabled and pinned to the organisation's CA, will refuse to associate with an evil twin because the evil twin cannot present a certificate signed by that CA. Configured incorrectly, with server validation disabled, or with the CA not pinned, the client will happily authenticate to anyone. The architectural decision is not just "use EAP-TLS" but "use EAP-TLS with strict server validation, configured by the organisation rather than by the user."

### 802.1X, the closest Layer 2 gets to architecture-first

**802.1X** is port-based access control, and it is the one Layer 2 mechanism that aligns cleanly with the principles in the introduction. The model is simple: when a device attaches to a port (wired or wireless), the port refuses to forward any frames other than the EAP authentication exchange itself until the device has authenticated. The port is, in effect, in a deny-by-default state. Authentication succeeds, the port opens; authentication fails, the port stays closed.

The components are three. The **supplicant** is the software on the connecting device that performs the EAP exchange, `wpa_supplicant` on Linux is the canonical open-source implementation. The **authenticator** is the network device, the switch or access point, that polices the port. The **authentication server** is the system that actually validates the credentials. RADIUS is the protocol the authenticator uses to talk to the authentication server, and **FreeRADIUS** is the open-source implementation that should be the default choice for any organisation deploying this. The authenticator does not need to know how authentication works; it just relays the EAP messages to the authentication server and enforces the server's verdict.

802.1X with EAP-TLS gives the architecture two properties it cannot get any other way at Layer 2. First, **fail-safe defaults at the port level**: nothing connects without authentication, no quiet implicit trust based on physical presence. Second, **dynamic policy assignment**: the authentication server can return attributes that tell the authenticator what VLAN to place the device into, what filters to apply, what bandwidth to allow. A device that authenticates as a workstation gets placed into the workstation VLAN. A device that authenticates as a printer goes into the printer VLAN. A device that fails authentication, or authenticates with a flagged certificate, goes into a **quarantine VLAN** with limited reachability, typically just enough to reach a remediation portal. The segmentation decision moves from being a port configuration applied in advance to being an authentication-time decision, which is the right place for it.

The cost is operational. 802.1X requires a working authentication server, working certificate infrastructure, supplicant software on every device, and a process for issuing and revoking certificates. None of this is technically difficult, but all of it requires sustained attention. The architectural reward is proportional: every Layer 2 attachment becomes an authenticated event. The implicit trust the layer was built around is replaced with explicit trust, evaluated at the point where the device meets the network.

### The architecture-first answer to Layer 2 attacks

Every conventional Layer 2 control discussed above, port security, DHCP snooping, Dynamic ARP Inspection, BPDU guard, root guard, native VLAN discipline, trunk pinning, is a patch on a layer whose default trust model is wrong. Each control works. Each requires per-port configuration, applied consistently, kept current, and verified continuously. Each is a place where the architecture depends on procedural correctness to maintain a security property the structure does not provide. This is exactly the pattern the introduction warned about: complex tooling accumulated over time to compensate for problems the underlying architecture created in the first place.

The architecture-first answer is to assume breach at Layer 2 and remove the assumption that Layer 2 controls are providing confidentiality or integrity at all. If every host treats every other host on the broadcast domain as untrusted, then the Layer 2 attacks lose their punch:

- ARP spoofing diverts frames to the attacker. Those frames carry encrypted payloads. The attacker sees ciphertext.
- MAC flooding turns the switch into a hub. The attacker sees every frame on the segment. Those frames carry encrypted payloads. The attacker sees ciphertext.
- VLAN hopping crosses the VLAN boundary. The attacker reaches hosts on other VLANs. Those hosts only accept authenticated, encrypted connections. The attacker has reachability to a TLS handshake they cannot complete.
- A rogue access point captures every frame in the air. The frames are encrypted at the link layer by WPA3 and again at the application layer by TLS or by the mesh VPN. The attacker has noise.

This is what the encrypted mesh VPN by default actually buys. A WireGuard tunnel between every pair of hosts means that every frame on the wire, wired or wireless, switched or routed, carries ciphertext that no Layer 2 attack can decrypt, because the keys are not on the network. The cryptography lives at the endpoints, where the data was produced and where it will be consumed. Everything between those endpoints carries opaque traffic, and the Layer 2 attacks that successfully position the attacker in the path do not give the attacker access to anything they can read.

The conventional Layer 2 controls do not stop being useful in this model. They become **defence in depth**. They contain the blast radius of operational mistakes, a misconfigured device, a misplugged cable, an employee plugging in a personal access point, and they keep the network functioning when those things happen. They are no longer the load-bearing mechanism that keeps data confidential, because the load-bearing mechanism is cryptography that does not depend on Layer 2 working correctly. Port security, DAI, and BPDU guard become operational hygiene rather than security primitives. That is the right place for them.

The corollary is that VLANs and 802.1X retain their importance, because they do something cryptography cannot: they keep unauthorised traffic out of the broadcast domain in the first place. Cryptography prevents the attacker from reading frames they capture; 802.1X prevents the attacker from being on the segment to capture them at all. The two mechanisms are doing different jobs and both are worth doing.

### Information leakage, the protocols that announce themselves

Two protocols deserve a specific note because they violate least functionality by default and frequently leak organisational information to anyone listening. **LLDP**, Link Layer Discovery Protocol, standardised as IEEE 802.1AB, and Cisco's proprietary **CDP**, Cisco Discovery Protocol, are designed to let network devices announce themselves to their neighbours. They broadcast switch model numbers, software versions, port identifiers, VLAN assignments, management IP addresses, and any other information the device manufacturer thought might be useful. An attacker who captures a single LLDP or CDP frame on a port learns most of what they need to plan further attacks.

The principle of least functionality says that capabilities a system does not need should not be enabled. Neither LLDP nor CDP is required for the network to function. They are convenience features for network administrators who want to walk into a wiring closet and immediately know what is plugged into what. The architecture-first answer is to disable them on every port that does not specifically need them, which, in most environments, is every port. Where they are needed, scope them to the trunks between known switches and disable them on every port that faces a host. The protocol classification places these in the **Single Layer** category, they operate within Layer 2 without contributing to the dependency chain, which is precisely the kind of protocol whose presence requires justification rather than being assumed.

### Layer 3 switches, the same analysis, with a routing function attached

A "Layer 3 switch" is a switch that also performs IP routing in hardware. The terminology is marketing-driven and the device blurs the layer boundary in practice, the same physical box does Layer 2 forwarding for frames within a VLAN and Layer 3 routing for frames between VLANs. The architectural analysis does not change. The Layer 2 forwarding is still the Layer 2 forwarding analysed above, with all the same trust assumptions and all the same attacks. The Layer 3 routing is the subject of the next chapter. A Layer 3 switch is two devices in one chassis, and the architect should reason about each function separately.

### The open-source stack

Layer 2 is one of the areas where the open-source stack is not just adequate but often preferable to vendor equipment. The Linux kernel includes a **VLAN-aware bridge** implementation that performs the same MAC learning, VLAN tagging, and STP participation as a vendor switch, with a configuration that lives in text files and is therefore amenable to infrastructure as code. For wireless access points, **hostapd** implements the AP side of the 802.11 stack including WPA2/WPA3-Enterprise, and **wpa_supplicant** implements the client side; both speak EAP and integrate with RADIUS. For authentication, **FreeRADIUS** with EAP-TLS is the reference open-source implementation, integrating with whatever identity store and certificate infrastructure the organisation is already running. For traffic capture and analysis, **tcpdump** and **tshark** at the command line and **Wireshark** in a graphical environment are the standard tools, all of them reading the same `pcap` format, all of them able to dissect every Layer 2 protocol mentioned in this chapter.

The architectural significance is that none of these tools requires accepting an unauditable binary into the trust path. The Linux bridge, hostapd, wpa_supplicant, FreeRADIUS, and the Wireshark family are all open-source projects with reproducible builds available, SBOMs that can be generated, and configurations that can be expressed in NixOS modules or Ansible playbooks and reproduced exactly across the fleet. A properly designed Layer 2 environment built from these components can be described in text, reviewed like source code, deployed reproducibly, and replaced or recovered from that description. This is what infrastructure as code looks like at Layer 2.

The corollary is the converse: a Layer 2 environment built from vendor switches with proprietary CLIs, undocumented behaviours, opaque software updates, and configurations that exist only as snapshots taken from running devices is the opposite of infrastructure as code. It is a collection of artisanal hand-tuned devices, each potentially different from the others, each potentially behaving differently after the next firmware update. The vendor switch may be necessary for performance reasons in some environments, high-density data centres, very high-speed links, but its presence in the trust path should be a justified exception, not the default.

### What an architect decides at Layer 2

The principles from the introduction reduce, at this layer, to a small number of explicit decisions:

**Where the broadcast domains are, and how big they are allowed to grow.** A broadcast domain is a blast radius. The architecture should know what each one contains, why it contains those things and not others, and what the consequence is if any device on the domain is compromised. Large flat networks are a failure of this analysis.

**What is allowed to attach to each port.** 802.1X with EAP-TLS, validated against certificates issued by the organisation's own CA, is the default. Every port. Wired and wireless. Devices that fail authentication go to a quarantine VLAN and nowhere else.

**What VLANs exist, what they are for, and how they are assigned.** Assignment should be authentication-driven (via 802.1X RADIUS attributes) rather than statically configured per port. Native VLAN should be unused. Trunks should tag every frame. Trunk negotiation should be off.

**What information the network is allowed to leak.** LLDP, CDP, and similar discovery protocols should be off everywhere except specific switch-to-switch links where they have a justified purpose.

**What runs in software the organisation controls.** Linux bridges, hostapd, FreeRADIUS, wpa_supplicant, described in NixOS configurations or Ansible playbooks, version-controlled, reproducibly deployed.

**And, most importantly: that Layer 2 is not a confidentiality or integrity boundary.** Frames on the broadcast domain are assumed to be readable by an adversary. The encrypted mesh VPN above carries the actual confidentiality and integrity guarantees. The Layer 2 controls keep the network operational and contain the blast radius of mistakes; they do not keep data safe. Anything above this layer that depends on Layer 2 being uncompromised has misunderstood the layer.

The architecture that emerges from these decisions is small. It uses a handful of well-understood primitives. It is describable in text and reproducible from that description. It treats every frame as adversarial and lets the cryptography above carry the trust. This is what the introduction's principles look like when applied to the data link layer: not a stack of vendor security products bolted onto a flat trusted LAN, but a structure in which the layer's well-known weaknesses have been answered by the choices the architect has already made.
